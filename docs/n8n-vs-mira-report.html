n8n vs mira-local

Side-by-side comparison of the research digest on the same data · memory profile, daily digest for 26 Sep 2026 (312 arXiv papers) · runs made 29–30 Sep 2026

The short version

  1. Same output. Replaying a real n8n run in mira-local reproduces it exactly: the same papers, prompts and statistics, and a byte-identical email. The replay found three mira-local bugs, now fixed. A live mira-local run on the same day chose 4 of n8n's 5 papers; independent LLM runs vary that much.
  2. The profiles are intact. All 6 profiles and 8 profile/mode combinations run in mira-local. They carry their own prompts, thresholds, arXiv categories, email styling and schedules, and n8n trigger names still route to them. A new test enforces this.
  3. Cost: the same. An uncached daily run costs about $6.70 on both; mira-local is about 1% cheaper because it skips two redundant LLM calls. 69% of the cost is the per-paper LLM stages, so the Jev pre-screen is the biggest saving available: about $2 per memory daily run.
  4. Speed: similar. Measured, mira-local was slower on two stages: PDF downloads (arXiv-bound) and the per-paper LLM stage, where it ran 8 calls in parallel against n8n's ~19. Both are fixed: PDFs are now cached, and parallelism is 20. The projected full run is ~8.6 min against n8n's ~8.7 min cold, and ~5.3 min when PDFs are already cached. The projection has not been measured yet.
  5. Reliability and footprint favor mira-local.
    • n8n's first run failed on a paper-ID formatting bug and wasted $5; mira-local handles that case.
    • n8n idles at 1.24 GiB of memory with a 4.4 GB image and a 1.3 GB database, against Prefect's 194 MB and an 8 MB database.

The profiles abstraction

Yes, it is fully maintained. A profile is still the unit everything hangs off. All profiles live in one file, configs/memory-innovation-profile.json, as in n8n. mira-local reads the same schema, so a profile edited for n8n works unchanged.

What each profile controls in mira-local:

  • topic focus
  • every LLM prompt (credibility, relevance, selection, deep analysis, report, trend, news)
  • thresholds
  • arXiv categories and keywords
  • lookback window per mode
  • email labels and colors
  • themes
  • news selection guidance
  • its own per-paper cache directory
  • its report history (which feeds trend analysis)
  • its schedules (configs/schedules.json)
  • realtime subscribers (configs/realtime.json)
  • Jev questions, which are built from the profile's own prompt

Changes during this work:

  • One copy of each profile. n8n kept duplicate copies of the mcbu and embedded profiles in separate files, which had drifted apart in their model settings. mira-local has a single source.
  • Two gaps closed: optical's daily mode had no schedule entry, and the realtime config did not list mcbu or embedded.
  • New test: tests/test_profiles.py checks that every profile/mode loads, has a schedule entry and appears in the realtime config, and that n8n's trigger names still route correctly.
Adding a profile
  1. Add it to configs/memory-innovation-profile.json (copy an existing one).
  2. Add one entry per mode to configs/schedules.json.
  3. Add it to configs/realtime.json (with no subscribers, alerts stay off).
  4. Run make test. The profile tests will point out anything missing.
Note: the n8n repo's configs/ and this repo's are now separate copies, so edit only mira-local's once you have cut over.

The first replay found three mira-local bugs, all now fixed with regression tests:

  • Abstracts. mira-local flattened line breaks in multi-paragraph abstracts; n8n keeps them. That changed prompts and cache lookups for 15 of 312 papers.
  • Authors and categories. n8n passes these to the LLM as JSON lists (["A","B"]); mira-local wrote "A, B". This changed the credibility, selection and deep-analysis prompts, and meant n8n's credibility cache was never reused.
  • A cross-profile cache leak. A leftover cache from the old CLI stored results by paper ID only. In the replay, a CXL result leaked into the memory digest, shrinking the ranked pool from 29 papers to 3. It has been removed; n8n never had it.

  • Failures cost money in n8n. Run 2084 spent $5.01 and then crashed before producing a report. The retry cost $2.07, because the per-paper results were cached. mira-local does not hit that failure.
  • Per-paper stages are 69% of the bill and scale with paper count. The Aug 31 weekly run scanned 1,665 papers. At the same ~1.5¢ per paper for both stages, that's roughly $25 for the per-paper stages plus ~$4 for the rest, so about $29 per memory weekly run. This is an estimate.
  • Biggest lever: the Jev pre-screen (jev_prescreen=true). For memory it skips 46–50% of the per-paper calls and keeps every paper that appeared in past reports: about $2.1–2.3 saved per daily run and ~$12 per weekly run. Jev's own cost is negligible.
  • Caching: the relevance cache carries over between n8n and mira-local. Credibility entries do not, because the PDF text differs. Copying n8n's cache at cutover therefore saves re-running relevance for any paper already processed.

Changes made during this comparison

  • Parity fixes: abstracts kept verbatim; authors and categories rendered as JSON lists; the cross-profile cache removed; cache entries now carry created_at, as n8n's do.
  • Speed: first pages now use n8n's caching extractor; per-paper LLM parallelism raised from 8 to 20 (MIRA_CLASSIFY_CONCURRENCY).
  • Profiles: added the optical daily schedule and the mcbu/embedded realtime entries; new tests/test_profiles.py.
  • Tooling: tools/n8n_export.py and tools/n8n_replay.py (see the README) can check parity against any future n8n run at no LLM cost.

Recommendations

  1. Run one more side-by-side, a weekly this time, to measure the projected speed with 20 parallel calls and cached PDFs, and to replay n8n's weekly run through the harness.
  2. At cutover, copy n8n's report-files/cache and report-files/prod into mira-local. The relevance cache and the trend history carry over.
  3. Turn on the Jev pre-screen for memory, CXL and storage after a short trial. It is the largest cost saving, at ~30%.
  4. Top up OpenRouter. About $19 is left, which covers roughly three daily runs or less than one weekly run.
  5. Decide on the three unmigrated n8n workflows. The Daily AI Trend Analyzer is live, runs every morning and has mostly been failing.
  6. Optional: switch mira-local to n8n's tool-call style for the LLM steps if you want the transport identical too. The prompts already are.

Limits of this comparison

  • One day and one profile (memory, daily). The replay proves the code paths match; one live run shows typical LLM variation, not a distribution.
  • n8n's "full run" time and cost combine two executions, because the first one crashed.
  • arXiv download speed varies with arXiv's load and the network, so the PDF-stage numbers are indicative.
  • The speed gains from today's fixes are projections until the next live run.
