Jev evaluation report

MIRA research triage · tests run 28–29 September 2026 · Jev model jev-latest (TypeSafe System One)

The short version

  1. Jev is fast and ranks papers much like our LLMs do, but it is stricter. About 0.12 s per paper, and its relevance ranking correlates 0.78–0.92 with the LLM's. It gives lower scores to loosely related papers, so it cannot simply replace the LLM's relevance score one-for-one.
  2. Best use in the weekly digests: a pre-screen. Jev drops papers that are clearly irrelevant before the expensive LLM steps. On two independent samples this skips 46–75% of LLM work for the memory, CXL and storage profiles, while keeping at least 99% of the papers the LLM would pass and every paper that has appeared in a real report. For optical it doesn't save enough to be worth it.
  3. Best use for the new realtime agent: the main filter. Jev scores every new paper and news article. The LLM only writes short summaries of the few items that make the email. This is built, tested and emailing hourly.
  4. Don't use Jev for topic labels, "actionable" flags, affiliation extraction, summaries, or picking the final papers. It agreed with the LLM on topic labels only 2–43% of the time, and it cannot write text.
  5. Two things are still unmeasured: Jev vs the LLM on picking news articles, and how long the LLM steps take for comparison. Both were blocked because the OpenRouter account ran low on credit.

What Jev is

Jev is TypeSafe's "System One" model. Unlike an LLM, it does not write text. You give it some content (the state) and a set of typed questions, and it returns an answer with probabilities for each one:

Question typeReturnsWhat we used it for
ScoreA position on levels you describe (e.g. 0–4), with probabilitiesPaper relevance (5 levels), institution credibility (4 levels), news-article relevance (4 levels)
ChoiceOne option from a list, with probabilitiesPrimary topic (the profile's own topic list), potential impact, actionable; picking the most relevant sentence of an abstract
NoulProbability that a yes/no statement is trueOnly in early smoke tests

Several questions about the same content go in one request and are answered in parallel. That is why one Jev call can judge relevance, topic, impact and actionable together in about 0.12 seconds. TypeSafe's own docs list where Jev is weak: generating text, arithmetic, dates, multi-step reasoning, and long inputs full of irrelevant detail. We designed around those.

Where Jev fits in our workflows (and where it doesn't)

We went through every place the workflows call an LLM and asked one question: is this step a judgment with a fixed set of answers, or does it produce text? Only judgments went to Jev. The workflow's logic stays the same everywhere.

Workflow stepJev?Why
Paper relevance score and keep/drop gateYes, as a pre-screenA graded judgment. Strong agreement with the LLM's ranking (see results).
Institution credibilityPartlyGood agreement when given the affiliation list. The list itself has to come from the LLM, because extracting it is text generation.
Author/affiliation extractionNoPulling names and institutions out of a PDF is extraction, which Jev isn't built for. The knowledge graph's author links depend on it.
Primary topic, actionable, impact labelsNoLow agreement, partly because the LLM invents labels outside the topic list.
Key findings, summaries, deep analysis, report, trend sectionNoThese produce text.
Final "top papers" selectionNoThe LLM's written reason for each pick feeds the deep analysis. Replacing it would change the workflow's logic.
Picking news articlesBuilt, not yet comparedPer-article relevance scores plus "top N" in code is a natural fit. The LLM side of the comparison is still to run.
Research-feasibility tier (T1–T4)CandidateA four-option choice, which suits Jev well. Not built or tested yet.
Realtime agent triageYes, main filterNeeds a decision in well under a second per item, around the clock. The LLM only summarizes the few items that pass.

How we tested

The baseline is our own LLM results. The weekly workflows cache every LLM judgment. That gave us 121,494 relevance/topic results and 114,069 credibility/affiliation results across four profiles (memory, CXL, storage, optical). Most came from Gemini 3.1 Pro; the memory profile also includes some from Gemini 3 Flash and the current production model, GPT-5.6 Terra. We also collected about 1,600 papers that appeared in past production reports, which we call featured papers.

  • Two independent samples of about 1,100–1,200 papers each, with no paper in both. Each profile's sample combined 150 random papers, extra papers the LLM passed, and extra featured papers. We tuned cutoffs on the first sample and checked them on the second.
  • Same inputs as the LLM. Titles and abstracts were re-fetched from arXiv, and first-page text was extracted for 200 papers (about 50 per profile).
  • Same preferences as the LLM. Jev's questions are built automatically from each profile's own prompt: its team description, relevance guidance and topic list. The parts meant only for the LLM, such as JSON formatting rules and the 1–10 numeric scale, are removed.
  • In total, about 4,950 Jev calls over the two samples, plus live runs on real weekly data.
How to read the agreement numbers Rank correlation (0 to 1): do both put papers in the same order? Agreement: share of papers where both make the same keep/drop call. Kappa: agreement corrected for luck; above 0.6 is substantial, above 0.8 is near-perfect. See the glossary.

Weekly pre-screen: skip the LLM for clearly irrelevant papers

How it works: Jev scores every fetched paper first. Papers below a very low cutoff skip the first-page PDF download, affiliation extraction and classification. Every other paper goes through the existing LLM pipeline unchanged. If Jev errors on a paper, that paper is kept.

Live test on real data

Last week's memory papers: 2,000 fetched, 930 screened out in 28 seconds. That is 46.5%, in line with the benchmark. During the run TypeSafe returned one server error (HTTP 520) for one paper. That paper was kept and sent on to the LLM, as designed.

One consequence: screened-out papers get no cached LLM result. Most backfill scripts already ignore low-relevance papers, but anything that uses every classified paper (for example the "all papers" statistics in the report) will see fewer papers. That is why the pre-screen is opt-in.

Realtime agent (MIRA Live)

A new agent that runs every hour and emails subscribers about new papers and news.

  1. Fetch the last 3 days of arXiv papers in the profile's categories, and crawl EE Times, SemiAnalysis, TrendForce and Digitimes.
  2. Skip anything already seen, using a per-profile ledger, so nothing is sent twice.
  3. Jev scores relevance for each new paper (title and abstract) and article (title and text). For papers that pass, it downloads the first page and scores the institutions' credibility.
  4. Rank what passed. The top 10 papers and top 8 articles get a 2–3 sentence summary from the LLM, written for the profile's preferences. If the LLM is unavailable, Jev picks the most relevant sentence from the abstract instead.
  5. Email a digest: title, link, source, authors, topic, relevance and credibility, a "High priority" tag, the summary and the abstract (or an excerpt for news). The next 30 papers are listed below it, with a count of any others.

What is not yet known

  • News selection vs the LLM. The benchmark script is ready (scripts/bench_jev_media.py), but the LLM side was blocked by the OpenRouter credit limit.
  • LLM speed and cost for comparison. The planned timing run (--llm-timing) hit the same credit limit. So we know Jev takes 0.12 s per paper, but haven't measured the matching LLM number here.
  • How consistent the LLM is with itself. Without it, we don't know the ceiling: if two LLM runs agree only 90% of the time, Jev's 86–94% is near the maximum.
  • The baseline is mostly older models. Most cached judgments are from Gemini 3.1 Pro; production now uses GPT-5.6 Terra. The cutoffs should be rechecked against the current model.
  • Credibility from the first page was tested on only about 50 papers per profile.
  • jev-latest is a moving target. The model behind the alias will change over time, and our cutoffs are calibrated to today's version.

Recommendations

  1. Turn on the pre-screen for memory, CXL and storage, after a short trial. Run 2–3 weekly digests with and without jev_prescreen and compare the selected papers and reports. If they match, make it the default for those three profiles. Keep optical off.
  2. Keep the LLM for everything that writes text, extracts affiliations, labels topics or makes the final selection.
  3. Tune the realtime agent's volume before adding more subscribers. Two options:
    • send arXiv papers once a day and keep news hourly
    • feature only "high priority" memory papers and list the rest
    Read a week of alerts and adjust ALERT_CUTOFFS.
  4. Finish the missing measurements once OpenRouter is topped up:
    • news selection (bench_jev_media.py)
    • LLM timing and cost (bench_jev.py --llm-timing 40)
    • a fresh baseline from the current production model
  5. Recalibrate when a model changes. Re-run the benchmark whenever the production LLM or Jev changes, or once a quarter. It costs only Jev calls, since it reuses cached LLM results.
  6. Next candidate: the research-feasibility tier (T1–T4) as a Jev choice, benchmarked against the current Claude Haiku judge.
  7. Get Jev approved like any other external API before company use (see below).

Setup and how to run

Account and key

  • Create a key at console.typesafe.ai and put it in .env as TYPESAFE_API_KEY=…. .env is gitignored, so never commit the key.
  • Python SDK: typesafe-sdk (MIT license), already in pyproject.toml. Model: jev-latest; override it with the JEV_MODEL environment variable (jev-preview also exists).
  • Limits from TypeSafe's docs: 64k tokens per request (32k for the content plus the longest question), and 1,200 requests/minute (limits are being adjusted). Billing is per input token; output is free. One of our paper judgments is about 400 tokens.
Data sent to TypeSafe Paper titles and abstracts, the first 2,500 characters of a paper's first page, the title and first 3,000 characters of news articles, and each profile's focus and relevance guidance. The papers and news are public. The profile text, though, describes what your team cares about. Treat Jev like the LLM endpoint: get it approved, or leave the realtime agent and pre-screen switched off.

Glossary

Level / cutoff
Jev's relevance answer is a position between 0 ("unrelated") and 4 ("core contribution"). A cutoff of 0.15 means "almost certainly unrelated".
LLM-passing paper
A paper the current LLM pipeline would keep: relevance and credibility at or above the profile's thresholds.
Featured paper
A paper that appeared in a real production report, the ones that matter most not to lose.
Rank correlation (Spearman)
1.0 means both put papers in exactly the same order; 0 means no relationship.
Agreement
Share of papers where Jev and the LLM make the same keep/drop decision.
Kappa
Agreement corrected for chance. Above 0.6 is substantial, above 0.8 near-perfect. It matters here because most papers are irrelevant, so "drop everything" would already score high raw agreement.
Precision / recall
Of the papers Jev passes, how many the LLM also passes (precision); of the papers the LLM passes, how many Jev also passes (recall).
Pre-screen
A cheap first filter that removes clearly irrelevant papers before the expensive stages, leaving everything else to run as before.
